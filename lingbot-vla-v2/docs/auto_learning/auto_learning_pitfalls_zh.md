# AutoLearning 启动链路「易错点」文档（2026-10-11 实战台账）

> **用途**：把 2026-10-11 这一轮"从 500 步 checkpoint 起续训却始终起不来"的真实排查过程沉淀成
> **可复用的易错清单**。每条都是**真机实测踩过的**，不是理论风险。
>
> **怎么用**：启动/排查 AL 训练前先扫一遍"快速自查表"（§1）；遇到症状直接跳到 §2 对应条目；
> 写脚本/长任务时看 §3（观测与停止的坑）；下结论前看 §4（判断口径）。

---

## §1 快速自查表（启动 AL 训练前逐条确认）

| # | 检查项 | 正确做法 | 做错的后果 |
|---|---|---|---|
| 1 | 模型标识是否**只有一处来源** | `--model-name` 显式给，或**不传**让它从 `--checkpoint` 尾部 4 段推导；launcher 与 worker 必须用**同一个函数** | launcher 与 worker 读写**不同缓存文件** ⇒ 覆盖率恒 0/50、训练永不启动 |
| 2 | 缓存文件名是否按模型分名 | `scout.<model-slug>.json` / `hardness.<model-slug>.json`（自动） | 换模型读写同一文件 ⇒ 旧缓存被覆盖、扫描成果丢失 |
| 3 | 覆盖检查是否**真的在跑** | 日志应出现 `[plan] 运行模式：reuse / incremental / full-scan` | 若恒为 `unknown`，说明覆盖检查被跳过（历史 bug，见 §2.1） |
| 4 | 覆盖数是否在**增长** | 起扫 1 分钟内应看到合计 N/50 上升 | 长时间恒 `0/50` = 写读不同文件（§2.2） |
| 5 | 预扫是否**只补 scout** | worker 环境带 `AL_SCAN_SKIP_HARDNESS=1`（launcher 自动注入） | worker 会顺手扫 50 个任务的 hardness ⇒ 白烧 2–3 小时且门控不看 |
| 6 | 训练进程**不得**带该开关 | `base_env()` 里显式为 `'0'`，且**禁止父进程透传** | 训练会跳过 hardness ⇒ 评测口径被破坏 |
| 7 | 训练是否真的在训练 | 看 `Step: N/20000 [..s/it]` 是否增长 | 只看到 `Start training` 不代表在跑（可能还在评测/扫描） |
| 8 | 多卡是否**同进程组** | `torchrun --nproc-per-node N`（训练侧）；判断依据是"父进程是 torchrun" | 单卡 worker 上 `AL_HARDNESS_SHARD=1` 静默失效 ⇒ 退化成全量单扫 |

## §2 核心易错点（按症状索引）

### §2.1 「launcher 的覆盖检查与扫描决策整块被跳过」——指纹与门控的绑定

**症状**：launcher 打印 `[plan] 运行模式：unknown`，扫描收尾时报"覆盖不完整"、**退出码 3**，
但日志里 `plan.step('启动训练')` 又像是要启动 —— 让人误判"启动了"。

**根因**（历史代码）：
```python
fingerprint = args.fingerprint          # 默认 None
if fingerprint is None:                 # ← 默认必然成立
    mode = 'unknown'; scan_target = []
    plan.step('缓存覆盖检查', '跳过（没有指纹，dry-run 模式）')
else:
    cov_before = check_coverage(...)    # ← 真正的覆盖检查 + 扫描决策（死代码）
```
"要不要做覆盖检查/扫描"被绑在"指纹算没算出来"上；而 2026-10-10 缓存已改为
「显式文件 + 模型名」寻址、**指纹不再参与缓存定位** ⇒ 这个绑定早已失效。

**修法**：判据改为 `if dry:`（`--dry-run` 才跳过）；指纹相关 CLI/代码**全部删除**
（用户 2026-10-11 决定）。回归测试锁死：源码里不得再出现 `if fingerprint is None:`。

**教训**：**`plan.step()` 打印的是"模板文本"，不是决策结果** —— 判断是否真启动，要看
`启动训练` 段落 + 后续进程/日志，而不是计划表。

---

### §2.2 「覆盖率恒 0/50」——同一份 run 里两套模型标识（**本轮最贵的坑**）

**症状**：扫描跑了 14 分钟，`合计 0/50` 一动不动；缓存目录里出现**三个** scout 文件。

**实测**（真机文件系统）：
```
scout.hf_ckpt.json                                         model='hf_ckpt'       记录=50  ← worker 写的
scout.train_al_v37_checkpoints_global_step_500_hf_ckpt.json model='robbyant…'     记录=50  ← launcher 读的
scout.json                                                 model='robbyant…'     记录=50
```

**根因**：两处各自实现"模型标识"，口径不同：
* launcher 侧 `scout_cache_file_for()`：`--checkpoint` 路径**尾部 4 段**；
* worker 侧 `base_env()` 里 `AL_MODEL_NAME`：旧口径 `Path(checkpoint).name` ⇒ **`hf_ckpt`**。
⇒ worker 写 A 文件、launcher 读 B 文件 ⇒ 门控永远看不到新记录。

**修法**：抽出 `resolve_cache_model()`（只解析标识、不碰文件），
`base_env()` 与 `scout_cache_file_for()` **都调它**；回归测试断言
`base_env()['AL_MODEL_NAME'] == scout_cache_file_for(...)` 且不等于 basename。

**验证证据**：修后同一启动方式，覆盖率 **T+38s 0/50 → T+3m58s 50/50**（真实增长）。

**教训**：**同一个概念不要两处实现**。同一 run 内"launcher 与 worker 必须同源"的字段，
要么单一来源下传，要么两边调同一个函数。

---

### §2.3 「预检读到 0 条记录」——用纯路径函数代替带迁移的函数

**症状**：`全集覆盖: 0/50（该缓存文件内 0 条记录）`（注意"**0 条**"），退出码 3。

**根因**：`scout_cache_file_for()` 里用了纯路径的 `scoped_cache_path()`，
而"把旧的无后缀缓存**复制**成 scoped 名"这一步在 `ensure_scoped_cache_file()` 里 —— 没被调用
⇒ 指向一个**尚不存在**的文件。

**区分"0 条" vs "50 条但 0 命中"**：
| 日志 | 含义 |
|---|---|
| `该缓存文件内 0 条记录` | 文件不存在/空 ⇒ 路径算错（本条） |
| `该缓存文件内 50 条记录；覆盖 0/50` | 文件在，但**记录全部判无效**（§2.2：model 不符） |

**教训**：**"路径解析"与"文件准备"要一起提供**，不能只暴露一半。

---

### §2.4 「换模型/走不同 run 时旧缓存被静默覆盖」——固定文件名 + 单 model 槽位

**症状**：base 权重的 50/50 scout 缓存，在从 `global_step_500` 起训后**被覆盖**。

**根因**：缓存文件是"固定文件名 + 顶层单个 `model` 字段"，换模型时 `store()` 走
`_blank()` 重建 + `os.replace()` ⇒ **覆盖同一文件**，无任何自动存档。

**修法**：缓存文件按模型分名（`scout.<slug>.json`）；首次使用 scoped 名时把旧文件**复制**过去
（只复制不删除）；`AL_CACHE_SHARED=1` 可回退单文件行为。
`model` 字段的一致性校验**保留**（防手工拷错文件、防迁移后字段过期）。

---

### §2.5 「预扫为什么要几小时」——门控只看 scout，worker 却把 hardness 也扫了

**实测数据**（同一次预扫）：
| 阶段 | 耗时 | 说明 |
|---|---|---|
| **scout** | 每任务 6.5–24 s ⇒ 50 任务/6 片 **≈4 分钟** | 门控**只**看这个 |
| **hardness** | 每任务 15–20 分钟（`data` 占 95%）⇒ 50 任务 **2–3 小时** | **门控完全不看** |

**根因**：launcher 的覆盖检查只查 scout 缓存，但扫描 worker 走的是同一条 `build.py` 全量装配路径，
bootstrap 队列跑空后继续走进 `_select()` ⇒ 给挑中的任务算 hardness。

**修法**：新增 `AL_SCAN_SKIP_HARDNESS=1`，**只注入扫描 worker**：
bootstrap 队列一空即 `scheduler._finish('scan_only_scout_done')` 并返回 None ⇒ 不算 hardness、不进训练。

**踩坑（单测抓出）**：`base_env()` 会把父进程所有 `AL_*` **自动透传**，
且透传发生在返回字典构造**之前** ⇒ 父进程 shell 若带同名变量，会**盖掉**训练侧显式的 `'0'`
⇒ 训练静默跳过 hardness。修法：**在透传阶段 `pop` 掉该键**。

**教训**：新增"只对某类子进程生效"的开关时，**必须同时防父进程透传污染另一类子进程**。

---

### §2.6 「多卡分摊扫同一个任务」为什么没生效——分片要求同进程组

**机制**（`backend.py` 已实现）：`ids_all[rank::world]` 交错切片 + `all_gather_object` 汇总
（含重复/缺失校验）+ 逐样本噪声绑定（换批不换噪声）。

**成立条件**：`dist.is_initialized() and world_size > 1`，否则**静默退回全卡全量**。

| 路径 | 进程组 | 分片 |
|---|---|---|
| 训练循环（进任务时扫） | **6 卡同 torchrun** | ✅ 生效（实测日志：`rank0/6 本 rank 43/255（6 卡分片，交错切片 ids[0::6]）`） |
| 预扫 worker | 每片 1 卡（`N_GPU=1`） | ❌ 退回全量 ⇒ 退化成"6 个 worker 各扫一个任务" |

**实测收益**（`pick_dual_bottles`，255 样本）：
| | 单卡 | 6 卡分片 |
|---|---|---|
| 单任务墙钟 | ≈21 分钟 | **≈4 分钟**（每卡 42–43 样本，`data` 仍占 83%） |

**重要澄清**：分片**不降低总工作量**（总样本数不变）⇒ 总墙钟与"6 卡各扫一个任务"同量级；
收益是**单任务延迟 ÷5–6**，而训练里"进任务就要它的 hardness"⇒ **单任务延迟才是卡顿来源**。

## §3 观测与操作的坑（脚本/长任务）

### §3.1 自匹配
`pgrep -f "train_lingbotvla.py"` 会匹配**执行它的那条命令自身** ⇒ 永远判"在跑"。
用方括号：`pgrep -f "[t]rain_lingbotvla.py"`。

### §3.2 数进程 ≠ 数卡
| 命令 | 陷阱 |
|---|---|
| `pgrep -cf "[t]asks/vla/train_lingbotvla.py"` | 会把 **bash/train.sh/torchrun** 也算进去（6 rank 数成 8） |
| 用环境变量 `WORLD_SIZE` 判 rank | **dataloader/编译 worker 继承父进程环境** ⇒ 6 rank 数成 **54** |
| **正确判据** | 该进程是 `torch.distributed.run` 的**直接子进程**（读 `/proc/<pid>/stat` 的 ppid） |

### §3.3 停进程：别"边枚举边杀"
**症状**：连续几轮 `kill -9` 后，`pgrep` 数字**纹丝不动**（12 rank / 6 train.sh / 6 torchrun）。
**根因**：在**同一次调用里**枚举 `/proc` 再逐个 kill，枚举到的列表本身在变；且部分 PID 是包装层。
**正确做法**：
```bash
pkill -9 -f "[t]rain.sh tasks/vla"
pkill -9 -f "[t]orch.distributed.run"
pkill -9 -f "[t]asks/vla/train_lingbotvla.py"
pkill -9 -f "[a]l_launch.py"
sleep 9
# 然后再复查（睡够再数，避免竞态）
```
**先验证权限**：单独 `kill -9 <pid>; echo $?` 确认能杀（实测 `rc=0` 且进程消失）。

### §3.4 别用"瞬时 GPU 利用率"判死活
扫描/评测阶段瓶颈在**数据加载**（`data 118s / score 9s`），GPU 计算单元**本来就空闲**。
`rocm-smi --showuse` 显示 0% 时，进程可能正在满负荷读帧。
**判活四件套**：进程数 + 显存占用 + 日志时间戳是否在更新 + 日志是否在推进（`hardness] 进度` / `Step`）。

### §3.5 别把"旧日志"当新证据
一次 restart 失败是因为**重定向到了同一个日志文件**，而我读到的仍是上一轮的失败日志
（`stat` 显示 mtime 早于本次启动）。**每次启动用新日志名**（`launch_<run>_runN.log`），
读日志前先看 `mtime`。

## §4 判断与表述的坑（下结论前自查）

| 易错 | 正确做法 |
|---|---|
| 把**外推**说成**实测**（"2–3 小时"其实是估算） | 分开标注：**实测**（含时间戳/数字）vs **外推**（写清推算依据） |
| 把**累计/顺序总时长**说成**要等这么久** | 说清这笔时间发生在**哪个阶段**：启动前置 / 训练中穿插 / 整个 run 累计 |
| 两个量混在一句（总工作量 vs 单任务延迟） | 分开列，各自给数 |
| 用旧口径描述当前运行（"每个任务做完 scout 就扫 hardness"） | 读**当前**日志确认顺序：先全部 scout → 挑一个任务 → 扫它的 hardness |
| 拿"看起来正常"当结论 | 查**硬指标**：`Step` 是否增长、覆盖数是否增长、致命错误计数（OOM/PassManager/SIGABRT/Traceback） |
| 报数字不给出处 | 每个结论附来源（哪个文件/哪一行/哪个指标名） |

**本轮的三个误报**（自省）：
1. 把 `plan.step('启动训练')` 当成"已启动"（§2.1）；
2. 把 `0/50` 归因为"分片/路径"而未先确认"到底写到了哪个文件"（§2.2）；
3. 用"GPU 忙卡 0"推断训练死了（§3.4）。

|---|---|

## §6 一页总结（五条最贵的教训）

1. **单一来源**：同一概念（模型标识/缓存路径）只能有一处实现，否则会出现"门控永远看不到结果"。
2. **门控与开销要对齐**：门控只看 scout，就不要让预扫去算 hardness；否则白烧几小时且不被检查。
3. **子进程开关要防污染**：只给 A 类子进程生效的开关，必须显式屏蔽 B 类（父进程透传是隐蔽通道）。
4. **先确认"东西写到哪个文件了"**：`0/50` 与"0 条记录"是两种完全不同的故障，别混着猜。
5. **判活要看四件套，判结论要分实测/外推**：瞬时利用率与模板日志都会骗人。
